## QA-06: entrega del perfil

La gestión de invitaciones respeta la política y los permisos del servidor:
emisión, reemisión, revocación y contraste informativo de nombre. El backend
decide la elegibilidad; un contraste de nombre no acredita identidad ni edad.

La recepción conserva el enlace exclusivamente en memoria y retira su token de
la URL con replaceState antes de cargar los demás recursos. Login y registro
regresan a /entrega; abrir el enlace no realiza el canje automáticamente.
La transferencia requiere confirmación explícita y declaración SELF vigente.

### Correcciones encontradas durante la revisión final

Las nuevas pruebas reprodujeron dos fallos de la implementación inicial: el
indicador global afectaba otras cuentas/invitaciones y una revisión incierta no
tenía una salida explícita para limpiar su aviso.

Ahora cada intento se asocia a una cuenta y una invitación. Solo se persiste el
valor booleano "1" bajo una clave opaca SHA-256 de esa combinación; no se guardan
el token, DNI, correo, nombre, resultado privado ni datos médicos en ese
indicador. La huella no sirve como credencial de canje ni permite recuperar el
token aleatorio. El DNI tampoco aparece en el mensaje visible si el servidor
lo devuelve textualmente en un error del contraste.

El indicador se escribe antes de enviar. Una respuesta definitiva lo elimina
solamente para ese intento. Red, timeout y 5xx dejan el resultado incierto y
bloquean un segundo envío. No se anuncia una cancelación ni se reintenta
automáticamente una operación que pudo llegar al servidor.

Atrás y los enlaces internos conservan el modelo en memoria. La salida permite
consultar Personas, comprobar el resultado y cerrar explícitamente esa revisión
sin otro POST. El botón solo se habilita después de visitar Personas; esta
acción expresa la comprobación del usuario y no una verificación automática de
que el servidor no guardó.

Logout elimina modelos y resultados privados en memoria; conserva únicamente
el aviso opaco de esa cuenta/invitación. Una respuesta tardía no restaura datos
de una cuenta cerrada ni borra su aviso. Otra cuenta u otro enlace no hereda el
bloqueo. Cerrar una revisión no elimina otra que siga pendiente.

Si se recarga o cierra la página, el token se pierde. La pantalla pide comprobar
Personas y reabrir el correo. Reabrir el mismo enlace con la misma cuenta
recupera su aviso persistente y exige revisar Personas antes de habilitar una
nueva acción explícita. No se pueden recuperar automáticamente el token ni el
resultado tras cerrar el navegador. Si el almacenamiento está bloqueado, no se
promete persistencia: se exige la comprobación y permanece la advertencia de
recuperación; no se persiste ninguna credencial como alternativa.

### Evidencia de interfaz y cobertura

Se recorrió en navegador real contra el backend local aislado:

1. Invitación sin sesión, con URL saneada /entrega.
2. Login con cuenta ajena, rechazo 403 sin datos del perfil.
3. Cierre/cambio de cuenta y retorno al mismo flujo.
4. Canje real completado por el backend y respuesta descartada deliberadamente
   por un proxy local de prueba, sin modificar el servicio.
5. Estado incierto, consulta de Personas, rol PRINCIPAL y registro ficticio
   original conservado.
6. Atrás conserva la incertidumbre y no vuelve a enviar.
7. Cierre explícito después de comprobar Personas, sin afirmar cancelación.
8. Recarga muestra instrucciones para reabrir el correo, sin token persistido.

El proxy contó un canje exitoso, un rechazo por cuenta ajena y una respuesta
exitosa descartada. Se apagaron los procesos locales al terminar.
Se mostraron capturas del perfil conservado, la advertencia, su cierre y la
recuperación tras recarga. La pantalla de entrega se comprobó a 390 x 844:
ancho del documento 390 px, sin desbordamiento horizontal en esa vista.

Las pruebas web usan JSDOM/adaptadores HTTP para login, registro, rutas,
doble clic, errores, Atrás y aislamiento del estado. La integración adicional
usa HTTP real con H2: cuenta ajena, invitación inexistente/vencida/revocada/
utilizada, segundo canje, actualización de roles, declaración SELF, conservación
de versiones/autores y notificación. La pérdida de respuesta se simula en el
cliente después de una transferencia real: no es una caída real de Internet.
No se confunden estas pruebas con Google OAuth, correo externo o RENIEC reales.

## Controles que corresponden al hosting

Pendientes de aplicar o verificar por quien administre el despliegue:

- Redactar /entrega/<token> desde el primer proxy/CDN y en access logs,
  registros de errores, trazas y exportaciones de analítica. La petición inicial
  llega al hosting antes de que el navegador pueda retirar el token.
- Excluir el cuerpo de canje, DNI, Authorization y credenciales de APM,
  seguimiento de errores, grabaciones de sesión y logs de request/response.
  No registrar objetos completos de Axios.
- Emitir Referrer-Policy: no-referrer como cabecera HTTP, además del meta
  no-referrer existente. Revisar redirecciones: no trasladar el token a otro
  dominio ni usarlo como identificador de seguimiento.
- Usar HTTPS y Cache-Control: no-store para las rutas sensibles y sus
  respuestas. Verificar CDN, service workers y redirecciones.
- Si hay CSP, autorizar correctamente el saneamiento temprano de URL sin
  debilitar la política global; no añadir scripts de seguimiento antes de él.

No se cambió configuración de producción. La redacción del lado del cliente
no puede garantizar que un proveedor de hosting ya configurado no registre la
petición inicial. Esa comprobación queda pendiente antes del despliegue.

## Limitaciones y comprobaciones pendientes

- Google OAuth real requiere su configuración y una cuenta de pruebas
  autorizada; no estaba configurado en el entorno aislado.
- Registro/login y retorno se cubrieron con pruebas de componentes; el login,
  cambio de cuenta y retorno también se recorrieron en navegador/HTTP real.
- Cierre completo del navegador y particularidades de beforeunload entre
  navegadores requieren comprobación manual; la seguridad no depende de que
  ese diálogo se muestre.
- Exportar bundles no equivale a compilar/instalar binarios nativos: quedan
  pendientes la ejecución física de Android/iOS y sus permisos.
- Las pruebas de base de datos ejecutadas usan H2 local; no se usaron
  PostgreSQL externo, SMTP real, RENIEC real ni datos personales.
- La política de logs, referencia y caché del hosting no se verificó en
  producción y debe validarse antes del despliegue.
